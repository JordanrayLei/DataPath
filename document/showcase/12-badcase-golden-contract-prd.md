# Bad Case—Golden 契约闭环 PRD

## 1. 执行摘要

### 1.1 问题陈述

点赞、点踩和问数记录只能表达用户态度，无法说明正确指标、正确终态、时间维度、过滤条件和期望结果。没有结构化正确答案，修复容易过拟合当前问题，也无法证明没有破坏已有能力。

### 1.2 解决方案

将线上反馈关联到完整执行现场，经质量运营人员确认问题与根因后，建立人工确认的 Golden 契约。修复发布前自动运行当前问题、同指标及语义冲突指标的受影响回归；任何安全门禁或 Golden 失败都阻止发布。

### 1.3 成功标准

| 类型 | 指标 | MVP 目标 |
| --- | --- | ---: |
| 可处理性 | 有效 Bad Case 可归因率 | ≥ 90% |
| 契约质量 | 已确认 Bad Case 的 Golden 完整率 | 100% |
| 回归控制 | 受影响 Golden 回归覆盖率 | 100% |
| 发布安全 | 绕过验证发布次数 | 0 |
| 修复效果 | 同类问题 30 日复发率 | ≤ 5% |
| 运营效率 | Bad Case 中位关闭时间 | ≤ 3 个工作日 |

当前项目已具备 Bad Case、Golden、发布门禁和相关工程验证；关闭时长、复发率等属于下一阶段真实运营目标。

## 2. 用户体验与功能

### 2.1 用户角色

| 角色 | 目标 | 核心权限 |
| --- | --- | --- |
| 业务用户 | 低成本报告错误 | 提交反馈、补充描述、查看处理状态 |
| 质量运营人员 | 还原现场、归因、确认 Golden | 确认、分派、验证、关闭 |
| 指标管理员 | 修复不改变计算结果的语义资产 | 编辑草稿、提交验证 |
| 数据平台管理员 | 处理权限、Join、Schema 等结构问题 | 查看证据、修复治理资产 |
| 发布审核员 | 控制修复版本上线 | 查看门禁、批准或拒绝 |

### 2.2 Bad Case 定义

Bad Case 是系统实际行为与人工确认的正确契约不一致，且能够关联到一次真实或可复现问数请求的问题。

有效记录至少包含：

- 原始问题、会话上下文和用户可见业务范围；
- 实际终态、候选指标、指标版本、Query DSL、血缘、Evidence 和结果摘要；
- 用户反馈类型与补充描述；
- 人工确认的根因层级和正确契约；
- 处理人、状态、修复版本和验证记录。

用户不喜欢结果样式、提出新需求或无法提供可复现上下文，不直接视为有效 Bad Case，应分类为体验建议、功能需求或待补充。

### 2.3 用户故事与验收标准

#### US-01：提交反馈

> 作为业务用户，我希望在结果旁直接说明哪里不对，从而不用手工整理 SQL 和截图。

验收标准：

- 支持错误指标、条件错误、结果错误、解释不清、权限疑问和其他分类；
- 自动关联 query_run_id、会话、指标版本、DSL、Evidence 和结果摘要；
- 敏感明细按权限脱敏；
- 提交后生成可查询的反馈编号。

#### US-02：确认与归因

> 作为质量运营人员，我希望查看完整执行现场并按产品阶段归因，从而把问题交给正确负责人。

验收标准：

- 工作台展示用户问题、实际行为、关键 Evidence 和资产状态；
- 根因至少覆盖输入理解、指标召回、候选裁决、上下文、DSL、Join、权限、Schema、执行和解释；
- 支持确认、驳回、合并重复问题和要求补充；
- 权限、Join、Schema 和公式问题必须路由到对应治理模块，不能用关键词补丁掩盖。

#### US-03：建立 Golden 契约

> 作为质量运营人员，我希望定义机器可验证的正确答案，从而让修复结果不依赖口头判断。

验收标准：

- Golden 必须定义预期终态 `SUCCESS/CLARIFY/REJECT/BLOCKED`；
- `SUCCESS` 至少包含正确指标版本、时间、维度、过滤、DSL 形态与 Oracle；
- 非成功终态包含必须触发的原因码和禁止行为；
- 原系统输出不能自动成为 Golden；
- Golden 必须记录确认人、业务域、版本和生效状态。

#### US-04：修复语义资产

> 作为指标管理员，我希望在工作台修改允许范围内的语义资产，从而快速验证语义问题。

验收标准：

- 仅允许修改别名、正反例、区分说明等不改变计算结果的内容；
- 修改形成草稿和差异记录，不直接影响生产；
- 公式、Join、权限、Schema 和代码问题跳转对应模块；
- 每次验证绑定唯一修复草稿指纹。

#### US-05：受影响回归与发布

> 作为发布审核员，我希望看到当前问题和相关 Golden 的验证结果，从而避免修好一个问题却破坏其他能力。

验收标准：

- 回归范围至少包含当前用例、同指标 Active Golden、原错误命中指标和语义冲突指标；
- 安全用例和未发布资产用例强制执行；
- 当前问题或任一受影响 Golden 失败时禁止发布；
- 发布记录关联反馈、Bad Case、Golden、草稿、测评运行和审批人；
- 发布后自动进入复发监控。

### 2.4 主流程

```text
用户提交反馈
→ 自动冻结执行现场
→ 质量运营确认有效性
→ 分层归因与分派
→ 人工定义 Golden
→ 创建修复草稿
→ 计算受影响回归范围
→ 运行当前、相关 Golden 与安全门禁
→ 审核发布
→ 监控复发
→ 关闭或重新打开
```

### 2.5 状态机

| 状态 | 含义 | 允许动作 |
| --- | --- | --- |
| `PENDING` | 新反馈待确认 | 确认、驳回、补充 |
| `CONFIRMED` | 已确认 Bad Case | 归因、分派、建 Golden |
| `CONTRACTED` | Golden 已确认 | 创建修复 |
| `FIXING` | 修复中 | 更新草稿、发起验证 |
| `VALIDATING` | 正在回归 | 查看进度、取消 |
| `VALIDATED` | 全部门禁通过 | 提交发布 |
| `PUBLISHED` | 修复已发布 | 观察、关闭 |
| `CLOSED` | 已验证关闭 | 查看、重新打开 |
| `REJECTED` | 非有效 Bad Case | 查看理由 |
| `BLOCKED` | 等待外部治理修复 | 关联治理任务 |

### 2.6 异常规则

| 异常 | 产品处理 |
| --- | --- |
| 执行现场缺失 | 标记待补充，不允许确认 Golden |
| Golden 缺少正确指标或终态 | 不允许进入验证 |
| Oracle 不稳定 | 标记待人工确认或改用性质断言 |
| 回归中资产版本变化 | 取消本次结果，要求重新运行 |
| Schema 事件影响修复资产 | Bad Case 转 `BLOCKED` |
| 发布后同类问题复发 | 重新打开并关联原 Golden |

### 2.7 非目标

- 直接使用点赞点踩训练线上模型；
- 自动确认 Bad Case 或 Golden；
- 允许质量运营绕过权限和安全门禁；
- 在该工作台修改指标公式、Join 或 Schema；
- 对所有低价值反馈执行完整重流程。

## 3. AI 系统要求

### 3.1 AI 可执行范围

- 总结用户问题和执行 Evidence；
- 推荐可能的根因层级；
- 推荐相似 Bad Case 和相关 Golden；
- 为人工审核生成语义修复草稿。

AI 不得确认根因、Golden、Oracle、发布结果或安全例外。

### 3.2 评测策略

| 评测层 | 核心判断 |
| --- | --- |
| 单条契约 | 实际终态、指标、DSL、Oracle 和禁止行为是否满足 |
| 受影响范围 | 当前、同指标、错误指标和冲突指标 Golden 是否覆盖 |
| 安全门禁 | 危险执行、越权、未发布和受 Schema 影响资产是否为 0 |
| 归因建议 | Top-3 是否包含人工确认根因，仅作为辅助指标 |
| 修复收益 | 当前问题通过且既有严格通过率不下降 |

当前测评基线：

| 指标 | 结果 |
| --- | ---: |
| Development 严格通过 | 1,118 / 1,128 |
| Development 严格通过率 | 99.11% |
| 错误指标选择 | 0 |
| 危险执行 | 0 |

该结果用于版本基线，不等同于线上运营指标。

## 4. 技术规格

### 4.1 架构与数据流

```text
Query Run / Evidence → Feedback → BadCase
                                  ↓
Root Cause → GoldenContract → FixDraft
                                  ↓
Impact Selector → Evaluation Run → Publish Gate
                                  ↓
Asset Version / Audit / Recurrence Monitor
```

### 4.2 核心实体

| 实体 | 关键字段 |
| --- | --- |
| `Feedback` | query_run_id、type、comment、user_scope |
| `BadCase` | status、root_cause、severity、owner、duplicate_of |
| `GoldenContract` | expected_status、metric_version、dsl_shape、oracle、forbidden |
| `FixDraft` | asset_type、before、after、fingerprint |
| `EvaluationRun` | case_scope、results、safety_counts、baseline |
| `FixRelease` | version、approver、published_at、rollback_to |

### 4.3 集成点

- 问数服务：冻结问题、上下文、DSL、Evidence 和结果；
- 指标与语义中心：读取版本并创建有限修复草稿；
- 权限、Join、Schema 模块：接收结构问题；
- 测评服务：选择用例并执行 Oracle；
- 发布服务：校验门禁、切换版本和回滚；
- 埋点与审计：计算处理漏斗、关闭时间和复发率。

### 4.4 安全与隐私

- 反馈继承原查询的数据范围，不扩大可见性；
- 结果明细最小化保存，优先保存摘要和哈希；
- Golden 审核、修复发布与回滚采用分权；
- 所有状态迁移由服务端校验；
- 删除用户可识别信息不影响契约和审计链完整性。

### 4.5 性能与可靠性目标

| 场景 | 目标 |
| --- | ---: |
| 提交反馈 P95 | ≤ 1 秒 |
| Bad Case 列表查询 P95 | ≤ 2 秒 |
| 执行现场冻结成功率 | ≥ 99.9% |
| 发布门禁一致性 | 100%，失败默认阻断 |

## 5. 风险与路线图

### 5.1 分阶段发布

- **MVP**：反馈、现场冻结、人工归因、Golden、当前与同指标回归、发布阻断；
- **V1.1**：重复问题合并、受影响范围推荐、批量运营和复发看板；
- **V2.0**：跨版本趋势、风险优先级和基于已确认案例的修复建议。

### 5.2 灰度与回滚

先只记录反馈和 Evidence；再对质量运营开放人工 Golden；随后启用影子回归；验证稳定后才让回归结果成为发布硬门禁。发布后若核心 Golden、安全门禁或线上复发指标异常，回滚语义资产版本并重新打开关联 Bad Case。

### 5.3 主要风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 反馈噪声高 | 运营成本过大 | 有效性确认、合并重复、风险排序 |
| 人工 Golden 错误 | 错误被固化 | 双人审核、高风险用例分权 |
| 修复过拟合 | 旧能力下降 | 扩大受影响回归和基线比较 |
| 闭环过重 | 处理周期过长 | 仅对高风险和可复现问题建完整契约 |
