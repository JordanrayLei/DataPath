# PRD：DataPath 可信 ChatBI

## 1. 产品背景

业务人员提出临时取数需求时，通常需要经过需求沟通、口径确认、数据定位、SQL 编写、结果校验和解释交付。自然语言问数可以缩短这条链路，但如果只是让大模型直接生成 SQL，会产生新的风险：

- 相似指标被错误识别；
- 时间、维度或筛选条件解析错误；
- 多表 Join 导致数据重复计算；
- 用户访问了超出职责范围的数据；
- Schema 变化后，旧指标和查询仍被继续使用；
- 答案表达流畅，但没有结果证据支持；
- 用户反馈没有形成可验证的修复闭环。

DataPath 的目标不是让 AI 自由访问数据库，而是在指标、权限、Join、Schema 和执行安全均可验证的边界内，完成从业务问题到可信数据答案的产品化链路。

## 2. 产品目标

### 2.1 用户目标

#### 业务分析用户

- 使用业务语言完成常见指标查询；
- 在问题存在歧义时获得明确的澄清选项；
- 看到结果使用的指标、时间范围和数据证据；
- 对错误结果提交低成本反馈。

#### 指标管理员

- 将业务口径建设为可发布、可检索、可追溯的指标资产；
- 使用 AI 生成语义草稿，降低新业务域冷启动成本；
- 处理语义 Bad Case，并通过回归控制修复发布。

#### 数据平台管理员

- 将物理数据表组织为受治理的业务域、模型和关系；
- 管理安全 Join 与跨事实计算；
- 在 Schema 变化后定位影响、阻断风险并恢复资产。

#### 质量运营

- 观察问数链路的质量和安全门禁；
- 将用户反馈转化为可归因、可验证、可关闭的问题单；
- 使用 Golden 和分层评测持续控制版本质量。

### 2.2 产品成功标准

产品成功不以“所有问题都有答案”为单一标准，而由四组结果共同判断。

| 维度 | 成功标准 |
| --- | --- |
| 安全 | 危险执行为零；权限、未发布资产和受影响资产均失败关闭 |
| 正确 | 指标、查询结构、Oracle 结果和 Evidence 通过评测 |
| 效率 | 用户能够减少从提问到获得可用答案的等待与人工往返 |
| 演进 | Bad Case 能够归因、形成 Golden、完成回归并关闭 |

核心产品指标为“每周被采用的可信答案数”。只有终态为 `SUCCESS`、完成执行与 Evidence 校验，并被用户继续使用、复制、导出或明确确认的答案，才计入采用。

## 3. 产品边界

### 3.1 本期范围

- 数据源扫描与业务域治理；
- 语义模型、共享维度和安全 Join；
- 指标定义、版本与发布状态；
- AI 语义预热及人工审核；
- 自然语言问数与多轮上下文；
- 有限候选裁决、Query DSL 与确定性 SQL 编译；
- 权限预检与租户级数据隔离；
- 结果图表、Evidence 与 Reflection；
- Schema 变化影响传播与恢复；
- 用户反馈、Bad Case、Golden 与回归测评；
- 测评监控与发布门禁。

### 3.2 本期不做

- 通用 ETL 和数据开发平台；
- 自助式大屏、复杂报表设计器；
- 允许用户直接执行自由 SQL；
- 由 AI 自动定义或修改指标公式；
- 绕过人工确认的自动发布；
- 对任意外部知识问题进行开放式回答。

## 4. 用户角色与工作区

| 角色 | 主要入口 | 核心任务 |
| --- | --- | --- |
| 业务分析用户 | 问数工作台 | 提问、追问、查看证据、采用或反馈 |
| 指标管理员 | 指标中心 | 定义指标、审核预热、发布版本 |
| 数据平台管理员 | 业务域与 Schema 管理 | 建模、治理 Join、处置结构影响 |
| 质量运营 | 质量运营工作台 | 处理 Bad Case、维护 Golden、运行测评 |

具体角色、资源和数据访问规则见[权限设计](08-permission-design.md)。

## 5. 产品全链路

```text
扫描数据源
→ 建立业务域与语义模型
→ 治理维度和安全 Join
→ 定义并发布指标
→ AI 生成语义预热草稿
→ 人工审核并应用语言资产
→ 用户自然语言提问
→ 权限与业务域预检
→ 指标检索和有限候选裁决
→ Query DSL 校验与确定性编译
→ 只读执行
→ Evidence 与 Reflection 校验
→ 返回答案、图表和证据
→ 用户采用或提交反馈
→ Bad Case 归因、Golden、修复与回归
```

Schema 变化作为横向控制链路：一旦底层结构变化影响模型、Join 或指标，系统传播影响并阻断相关问数，复核通过后才恢复发布。

完整的业务流程和角色操作流程见[产品流程图](06-product-flows.md)。

## 7. 功能需求

### 7.1 数据源接入

#### 用户故事

> 作为数据平台管理员，我希望验证数据源并扫描 Schema，以便把物理数据纳入后续治理。

#### 功能规则

- 支持配置受允许的数据源连接；
- 连接验证成功后才允许扫描；
- 扫描结果包含表、字段、类型和基础统计信息；
- 扫描只产生物理元数据，不自动发布业务模型；
- 数据连接凭证不在产品页面和普通日志中明文展示；
- 查询执行账户保持只读，并与编译或管理账户分离。

#### 异常处理

| 异常 | 系统行为 |
| --- | --- |
| 连接失败 | 保留配置草稿，显示可定位的失败原因 |
| 主机不在允许范围 | 拒绝连接 |
| 扫描中断 | 标记本次任务失败，不覆盖最近一次有效快照 |
| Schema 与快照不同 | 生成变化记录并进入影响分析 |

### 7.2 业务域与模型治理

#### 用户故事

> 作为数据平台管理员，我希望把相关物理表组织成独立业务域，并明确模型粒度、维度和关系，使问数只在可治理范围内运行。

#### 功能规则

- 一个业务域拥有独立模型、关系、指标和语义策略；
- 模型必须声明业务含义、粒度和唯一键；
- 共享维度必须声明可连接模型及连接键；
- Join 需记录两端模型、基数、类型和 Fanout 策略；
- 未发布或受影响的模型与 Join 不进入在线查询；
- 跨事实计算必须先分别聚合，再按治理关系合并。

### 7.3 指标中心

#### 用户故事

> 作为指标管理员，我希望将业务定义和计算口径发布为版本化指标，供问数和评测共同使用。

#### 指标字段

- 指标名称与唯一标识；
- 业务定义；
- 计算公式与聚合方式；
- 单位与格式；
- 默认时间字段；
- 所属业务域和模型；
- 可用维度；
- 血缘；
- Owner；
- 发布状态和版本。

#### 状态

| 状态 | 含义 | 是否进入问数 |
| --- | --- | --- |
| `DRAFT` | 正在编辑 | 否 |
| `IN_REVIEW` | 等待审核 | 否 |
| `PUBLISHED` | 已通过治理与发布 | 是 |
| `IMPACTED` | 受 Schema 或依赖变化影响 | 否 |
| `DEPRECATED` | 已下线 | 否 |

#### 发布规则

- 必填信息和语义完整度达到门槛；
- 别名不与其他已发布指标产生未处理冲突；
- 模型、维度和 Join 均可用；
- 关联测评通过；
- 发布产生不可变新版本，旧版本保留用于追溯。

### 7.4 AI 语义预热

#### 用户故事

> 作为指标管理员，我希望在指标发布前由 AI 扩展业务表达，以便新指标在第一批用户提问前具备基础语义覆盖。

#### 输入

- 已确认的指标名称、定义和公式；
- 业务域、模型、维度和血缘；
- 已有别名与语义策略；
- 相邻指标及其边界。

#### 输出

- 业务别名；
- 典型正向问法；
- 相邻指标反例；
- 语义完整度和待完善项。

#### 规则

- AI 只能生成草稿，不能修改指标公式和口径；
- 草稿按条展示，可接受、编辑或拒绝；
- 冲突检查在应用前执行；
- 只有人工确认的内容进入检索资产；
- 指标定义变化后，旧草稿需要失效或重新审核。

### 7.5 问数工作台

#### 用户故事

> 作为业务分析用户，我希望直接描述业务问题，并在一次会话中继续调整时间、维度和筛选条件。

#### 页面组成

- 会话标题与上下文状态；
- 问题输入框和示例问题；
- 用户问题与系统回答；
- 澄清选项或拒绝原因；
- 结果表格与图表；
- 指标、时间、权限范围和 Evidence；
- 采用、复制和反馈入口。

#### 多轮规则

- 允许继承上一轮已确认的指标、时间、维度和筛选；
- 用户明确提供的新条件覆盖旧条件；
- 指标发生变化时重新完成候选和权限校验；
- 身份或工作空间发生变化时不继承上下文；
- 上下文存在冲突时进入澄清，不自行猜测。

### 7.6 指标检索与有限候选裁决

#### 检索

系统从已发布且有权访问的指标中组合使用名称、别名、中文词法、BM25、正反例和向量召回，形成有限候选集。

#### 裁决

模型只能执行三类动作：

1. 在候选中选择唯一指标；
2. 返回需要用户确认的澄清选项；
3. 判断问题超出当前产品或业务域范围。

后端再次验证候选标识、指标版本、业务域、权限和置信条件。模型不得创造候选集之外的指标。

### 7.7 Query DSL、校验与编译

自然语言意图转化为受约束 Query DSL，至少包含：

- 指标和版本；
- 维度；
- 时间范围；
- 筛选；
- 排序；
- 行数限制；
- 多指标组合方式。

后端在编译前校验：

- 指标和版本已发布；
- 维度属于指标允许范围；
- 过滤字段和操作符合法；
- Join 已治理且路径安全；
- Schema 状态正常；
- 用户角色、业务域和数据范围允许；
- 查询成本处于阈值内；
- 请求不包含危险执行意图。

校验通过后，系统确定性生成参数化 SQL。大模型生成的自由 SQL 不进入执行器。

### 7.8 执行与可信答案

#### 执行规则

- 仅执行由系统编译并签发执行令牌的 Query Run；
- 执行时复核操作者、工作空间和有效期；
- SQL 使用只读账户；
- 租户范围由编译器注入；
- 超时、成本超限或结果异常时失败关闭。

#### Evidence

答案至少展示或保存：

- 指标与版本；
- 数值、单位和格式；
- 时间范围；
- 维度与筛选；
- 数据范围；
- Query ID；
- 结果行或聚合证据；
- 模型、Join 和血缘摘要。

#### Reflection

AI 可以基于 Evidence 生成业务解读，但必须检查：

- 数值和趋势是否有证据；
- 是否把相关性表达为因果关系；
- 是否引用不存在的维度或结果；
- 是否遗漏影响理解的重要范围。

未通过 Reflection 的内容不以成功答案返回。

### 7.9 Schema 影响管理

#### 用户故事

> 作为数据平台管理员，我希望在底层字段被删除、改名或改变类型时，立即看到受影响资产并阻止错误查询。

#### 变化类型

- 表或字段新增；
- 表或字段删除；
- 字段重命名；
- 数据类型变化；
- 主键、唯一键或关系变化。

#### 传播规则

```text
物理字段
→ 语义模型
→ 共享维度与 Join
→ 指标和语义资产
→ 在线问数与测评
```

- 影响根据确定性依赖关系计算；
- 受影响资产进入 `IMPACTED` 或业务域降级状态；
- 相关查询失败关闭；
- 修复物理映射后仍需复核模型、指标和语义资产；
- 回归通过并重新发布后恢复问数。

### 7.10 用户反馈与 Bad Case

业务用户可对一次 Query Run 提交反馈。系统自动关联当时的指标版本、DSL、结果、Evidence、权限和 Schema 状态。

质量运营完成：

1. 确认反馈是否为有效 Bad Case；
2. 选择正确指标和正确终态；
3. 归因到召回、裁决、查询结构、执行、解读、权限或 Schema；
4. 建立人工确认的 Golden；
5. 将问题路由到对应治理模块；
6. 验证当前问题和受影响回归；
7. 通过门禁后发布并关闭。

完整规则见[Bad Case 自助闭环 PRD](02-badcase-closure-prd.md)。

### 7.11 测评监控

测评报告需要展示：

- 总体通过率和通过数量；
- 按产品用例分类的结果；
- 指标选择、查询形态和 Oracle 结果；
- 权限、安全和可信门禁；
- 失败用例及关联资产；
- 当前使用的评测集、指标版本和环境。

发布门禁至少要求：

- 危险执行为零；
- 错误指标选择为零；
- 当前修复用例通过；
- 受影响 Golden 通过；
- 评测证据被冻结并可追溯。

## 8. 产品终态

每次问数必须落入一个明确终态：

| 终态 | 使用条件 | 页面表现 |
| --- | --- | --- |
| `SUCCESS` | 权限、语义、DSL、执行、Evidence 和 Reflection 均通过 | 返回答案、图表和证据 |
| `CLARIFY` | 存在合理歧义或缺少必要信息 | 提供有限澄清选项 |
| `REJECT` | 问题不属于已治理能力或业务域 | 说明支持边界，引导重新提问 |
| `BLOCKED` | 权限、Schema、发布状态或安全门禁不允许执行 | 说明阻断原因和下一步 |

`CLARIFY`、`REJECT` 和 `BLOCKED` 不是系统异常，而是可信问数的正常产品结果。

## 9. 关键异常与降级

| 场景 | 处理策略 |
| --- | --- |
| 没有召回到可靠指标 | `REJECT`，不生成临时指标 |
| 多个指标无法可靠区分 | `CLARIFY`，展示有限候选 |
| 身份无效或业务域未授权 | `BLOCKED`，不召回敏感候选 |
| Join 未治理或存在 Fanout 风险 | `BLOCKED` |
| 指标或模型受 Schema 影响 | `BLOCKED` |
| 查询超时或成本超限 | 终止执行，提示缩小范围 |
| Evidence 不完整 | 不返回成功解读 |
| Reflection 不通过 | 返回数据结果的受限状态或失败关闭 |
| AI 服务不可用 | 保留治理和确定性能力，提示暂时无法完成语义理解 |
| 向量召回不可用 | 降级到名称、别名和词法检索，并记录降级状态 |

## 10. 非功能需求

### 10.1 安全

- 所有分析查询只读；
- 权限由服务端执行；
- 数据连接凭证加密保存；
- 查询和治理操作可审计；
- Evidence 按角色脱敏；
- 身份、服务和执行令牌用途分离。

### 10.2 性能

- 提问后及时展示处理中状态；
- 检索、裁决、编译和执行阶段分别记录耗时；
- 超过阈值的查询提前阻断或提示缩小范围；
- 相同治理版本下允许复用安全的检索和元数据缓存。

### 10.3 可追溯

一次答案应能关联：

```text
用户问题
→ 身份与权限范围
→ 指标及版本
→ Query DSL
→ SQL 与 Query Run
→ 结果
→ Evidence 与 Reflection
→ 用户反馈
→ Bad Case / Golden / 修复版本
```

### 10.4 可观测

各阶段需要记录统一 `trace_id`，并区分业务终态、系统异常和安全阻断。具体事件及指标口径见[事件埋点方案](07-event-tracking-plan.md)。

## 11. 版本验收

### 11.1 P0 验收

| 编号 | 验收项 | 通过条件 |
| --- | --- | --- |
| P0-01 | 已发布指标问数 | 能完成检索、DSL、执行和 Evidence |
| P0-02 | 指标歧义 | 返回有限澄清，不擅自选择 |
| P0-03 | 超范围问题 | 正确拒绝，不创造指标 |
| P0-04 | 危险意图 | 不生成和执行危险 SQL |
| P0-05 | 租户权限 | 不同租户只能看到各自数据 |
| P0-06 | 未治理 Join | 查询被阻断 |
| P0-07 | Schema 变化 | 影响传播到模型和指标，相关查询失败关闭 |
| P0-08 | Evidence | 成功答案可追溯到指标、DSL 和结果 |
| P0-09 | 用户反馈 | 反馈与原 Query Run 完整关联 |
| P0-10 | 回归门禁 | Bad Case 修复未通过关联 Golden 时不能发布 |

### 11.2 P1 验收

- AI 预热草稿可以按条审核并应用；
- 多轮上下文能够正确继承与覆盖；
- 质量工作台支持筛选、分派、归因和关闭；
- 测评报告支持按用例类型定位失败；
- 指标和 Schema 变更形成完整版本记录；
- 治理写操作完成统一服务端权限校验和审计。

## 12. 数据验证

产品上线后的验证分为四层：

| 层级 | 关注指标 |
| --- | --- |
| 使用 | 有效提问用户、有效问题、连续追问、功能渗透 |
| 转化 | 提问到成功、成功到查看证据、成功到采用 |
| 质量 | 指标正确率、查询结构正确率、Oracle 通过率、可信答案率 |
| 闭环 | Bad Case 确认率、平均关闭时间、一次回归通过率、复发率 |

埋点不记录完整 SQL、令牌、连接凭证和未经处理的敏感结果。

## 13. 迭代优先级

### 第一阶段：可信执行底座

- 业务域、模型、指标和安全 Join；
- 权限预检与租户隔离；
- Query DSL、确定性编译和只读执行；
- 四类产品终态；
- Evidence。

### 第二阶段：降低治理成本

- 指标语义完整度；
- AI 语义预热；
- 人工审核和冲突检查；
- 多轮问数体验。

### 第三阶段：形成质量闭环

- 用户反馈和 Bad Case 工作台；
- Golden 契约；
- 分类评测与发布门禁；
- 质量监控。

### 第四阶段：适配真实数据变化

- Schema 差异检测；
- 影响传播和失败关闭；
- 修复复核与恢复发布；
- 完整权限审计与企业身份接入。
