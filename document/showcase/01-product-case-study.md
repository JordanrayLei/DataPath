# DataPath 项目复盘

## 起点

业务人员经常需要向数据团队提出临时取数需求，例如：

- 今年各区域支付实收金额是多少？
- 哪些商品导致退款率上升？
- 退款后净收入最近三个月如何变化？

传统流程依赖分析师理解问题、确认指标口径、寻找数据表、编写 SQL 和制作图表。ChatBI 可以缩短这条链路，但直接让大模型生成 SQL，会把原来的人工成本变成另一类风险：

1. **指标口径风险**：相似名称可能对应不同业务含义。
2. **多表关联风险**：错误 Join 或 Fanout 可能让结果成倍放大。
3. **权限风险**：Prompt 不能替代后端权限控制。
4. **执行风险**：大模型可能生成未授权字段、自由 SQL 或危险操作。
5. **持续可用风险**：模型、指标或数据库结构变化后，已有问题可能发生退化。
6. **反馈闭环风险**：用户点踩只能说明不满意，不能定义正确答案并防止复发。

## 谁会用

项目中的用户分成三类，他们对“可信”的关注点并不相同。

业务分析用户只关心能否用熟悉的业务语言拿到结果，以及系统为什么没有回答。指标或数据产品经理关心的是口径：指标怎么定义、哪些表达算同义、一次错误应该如何修复。平台管理员关心的则是数据连接、权限、Schema 变化和执行安全。

这三类人对应三个工作区：

| 用户 | 在 DataPath 中完成的事情 |
| --- | --- |
| 业务分析用户 | 提问、追问、查看图表与证据、确认采用或提交反馈 |
| 指标/数据产品经理 | 发布指标和业务语义、处理 Bad Case、维护 Golden |
| 平台管理员 | 连接并扫描数据源、维护访问边界、处理结构变化 |

## 产品目标

DataPath 不以“每个问题都能回答”为目标。相比回答率，项目更关注降低取数门槛后，指标口径、权限、查询执行和答案质量是否仍然可控。目标分成三层：

### 安全底线

- 危险执行为零；
- 未发布指标不能执行；
- 未发布或不安全 Join 不能执行；
- 用户不能绕过业务域和数据范围；
- 受 Schema 影响的资产必须失败关闭。

### 任务质量

- 正确识别指标；
- 正确解析时间、维度、筛选和排序；
- 可回答问题尽可能直接完成；
- 歧义问题正确澄清；
- 超范围问题正确拒绝；
- 查询结果经过 Oracle 或 Evidence 验证。

### 持续运营

- 用户错误可以转化为 Bad Case；
- Bad Case 可以形成 Golden 契约；
- 修复必须通过受影响回归；
- 指标变更产生不可变新版本；
- 可以持续观察关闭时间、一次通过率和复发率。

## 产品方案

### 1. 人工治理业务事实

系统自动扫描数据库的表、字段和类型，但不自动决定：

- 表的业务含义；
- 模型粒度；
- 业务唯一键；
- 指标公式；
- 指标单位；
- Join 业务关系；
- 跨事实聚合方式。

这些内容由负责业务事实的工作人员确认并发布。AI 只能基于已发布资产生成别名、典型问法和边界反例草稿。

### 2. 受治理的指标检索

检索对象不是原始字段，而是完整指标语义包：

- 名称；
- 别名；
- 业务定义；
- 公式和单位；
- 正向问法；
- 反向问法；
- 适用业务域；
- 可用维度；
- 模型和血缘；
- 指标版本。

在线检索组合使用：

- 完整名称匹配；
- 最长别名匹配；
- 中文词法；
- BM25；
- 正反例；
- 本地 BGE 向量；
- 可选 Reranker。

### 3. 有限候选裁决

大模型只能在后端提供的有限候选中：

- 选择唯一指标；
- 请求澄清；
- 判断超出范围。

它不能发明指标或修改公式。后端会验证候选签名、指标版本、置信度和权限。

### 4. Query DSL 和确定性编译

系统不执行大模型自由生成的 SQL。自然语言先转化为受约束 DSL：

```json
{
  "metrics": [
    {
      "metric_id": "M_PROD_REFUND_ADJUSTED_REVENUE",
      "metric_version": 1,
      "aggregation": "default"
    }
  ],
  "dimensions": [
    {
      "dimension_id": "D_MONTH"
    }
  ],
  "time_range": {
    "start": "2024-01-01",
    "end": "2024-12-31",
    "timezone": "Asia/Shanghai"
  },
  "limit": 100
}
```

后端验证指标、版本、维度、过滤、权限、Schema、成本和 Join，再由编译器确定性生成 SQL。

### 5. Semantic Join Graph

多表关系作为治理资产管理：

- 关系两端；
- Join 键；
- 基数；
- Join 类型；
- Fanout 策略；
- 验证快照；
- 发布状态和版本。

跨事实指标强制 `aggregate_before_join`，避免事实明细直接连接后产生重复计算。

### 6. Evidence 与 Reflection

执行结果先生成结构化 Evidence，包括：

- 指标和版本；
- 数值和单位；
- 时间范围；
- 维度；
- 比较信息；
- 计算方式；
- Query ID；
- 结果行引用。

AI 基于 Evidence 生成业务解读，Reflection 再检查结论是否具有证据支持。未通过校验的解读不会作为成功答案返回。

### 7. 四类产品终态

| 状态 | 产品含义 |
| --- | --- |
| `SUCCESS` | 语义、权限、DSL、执行和解读均通过 |
| `CLARIFY` | 存在合理歧义或缺少必要信息 |
| `REJECT` | 问题超出当前业务域或产品能力 |
| `BLOCKED` | 权限、Schema、发布状态或安全门禁不允许执行 |

### 8. Bad Case 与 Golden 回归

```text
用户反馈
→ 工作人员确认 Bad Case
→ 定义正确指标和预期状态
→ 修改可治理语义
→ 验证当前问题
→ 回归同指标 Active Golden
→ 通过门禁
→ 发布不可变指标新版本
```

指标公式、Join、Schema 和权限问题不能通过增加关键词修复，必须回到对应治理流程。

## 关键取舍

### 取舍 1：准确率与回答率

选择：优先正确澄清、拒绝和阻断，不追求所有问题都返回结果。

原因：企业数据场景中，错误但流畅的答案比无答案风险更高。

### 取舍 2：自动化与人工治理

选择：AI 生成语义建议，工作人员确认业务事实。

原因：大模型可以扩展表达，但不能独立知道企业内部指标口径。

### 取舍 3：开放能力与执行安全

选择：使用受约束 DSL 和已发布资产，而不是自由 Text-to-SQL。

代价：暂时无法回答任意探索性问题。

收益：查询可以在执行前验证，并能稳定回归。

### 取舍 4：完整 BI 与可信链路

选择：优先完成语义、权限、执行、Evidence 和质量闭环，没有重建完整 ETL、大屏和报表设计器。

原因：项目的核心差异是可信数据 Agent，而不是图表数量。

## 测评设计

项目建立了分层评测体系：

| 数据集 | 数量 | 用途 |
| --- | ---: | --- |
| Development | 1,128 | 功能开发与分类测评 |
| Regression | 470 | 修复后的稳定性回归 |
| Locked | 752 | 冻结场景和历史能力验证 |
| 合计 | 2,350 | — |

评测覆盖：

- 核心指标；
- 跨事实指标；
- 时间解析；
- 维度、排序和限制；
- 多轮上下文；
- 指标歧义；
- 权限与租户范围；
- 危险请求；
- 未治理 Join；
- Schema 变化；
- Evidence 与 Reflection。

可执行问题使用 ClickHouse Oracle 检查结果，不以 HTTP 200 或 SQL 成功作为正确标准。

## 当前结果

### 产品资产

- 42 张数据表；
- 442 个字段；
- 约 792.5 万行数据；
- 11 个语义模型；
- 10 个共享维度；
- 6 条已发布安全 Join；
- 9 个单事实指标；
- 2 个跨事实指标；
- 62 个审核别名；
- 220 条语义向量。

### Development 测评

| 指标 | 结果 |
| --- | ---: |
| 严格通过 | 1,118 / 1,128（99.11%） |
| 可回答用例首次直接完成 | 833 / 840（99.17%） |
| 检索 Top-1 | 836 / 840（99.52%） |
| 检索 Recall@3 | 836 / 840（99.52%） |
| 错误指标选择 | 0 |
| 危险执行 | 0 |

### 工程质量

- 129 项自动化测试通过；
- 覆盖权限防绕过和只读执行；
- 真实 DDL 验收覆盖删表、删字段、改类型和恢复；
- 前端支持数据接入、业务域治理、指标发布、Bad Case 和 Golden 回归。

## 后续规划

### Phase 1：降低新业务域接入成本

- 导入历史 SQL；
- 识别候选事实表、维度表和 Join；
- 自动生成指标候选；
- 自动生成初始 Golden；
- 记录每个业务域的治理人天。

### Phase 2：从问数升级到分析任务

- 新增 Analysis Plan；
- 支持多查询步骤；
- 支持指标变化拆解；
- 计算维度贡献和未解释残差；
- 生成结构化经营简报。

### Phase 3：进入真实业务工作流

- 指标订阅；
- 异常主动触发；
- 报告审批；
- 企业协作工具推送；
- 审批后的受控业务动作。
