# DataPath 指标体系与测评方法

## 一、指标设计原则

ChatBI 的质量不能只用 SQL 执行成功率或请求回答率衡量。DataPath 将指标拆为：

1. 用户是否获得可用结果；
2. 指标和查询是否正确；
3. 权限和执行是否安全；
4. 错误能否持续修复；
5. 新业务域能否低成本上线。

## 二、北极星指标

产品进入真实使用阶段后的北极星指标定义为：

> 每周被业务用户明确采用的可信分析任务数。

一条分析任务需要同时满足：

- 查询成功；
- 指标、时间、维度和结果满足正确契约；
- 权限和安全门禁通过；
- 解读具有 Evidence 支持；
- 用户执行“结果可直接使用”的明确采用动作。

该指标避免将页面访问、SQL 执行或自动回归误认为真实业务价值。

## 三、核心指标体系

### 3.1 任务质量

| 指标 | 定义 |
| --- | --- |
| 严格通过率 | 终态、指标、DSL、结果、图表和 Reflection 全部满足预期的比例 |
| 首次直接完成率 | 可回答问题在第一轮直接正确完成的比例 |
| 人工修正率 | 用户明确表示进行人工修正的结果占比 |
| 平均澄清轮数 | 用户获得最终结果前经历的澄清次数 |
| 结果采用率 | 用户明确确认可直接使用的结果占比 |

### 3.2 指标检索

| 指标 | 定义 |
| --- | --- |
| Top-1 | 排名第一的召回指标与正确指标一致 |
| Recall@3 | 正确指标是否进入前三候选 |
| 错误指标选择率 | 系统以 `SUCCESS` 放行错误指标的比例 |
| 澄清精度 | 实际需要澄清的问题中被正确澄清的比例 |
| 拒绝精度 | 超范围问题中被正确拒绝的比例 |

### 3.3 查询正确性

检查：

- 指标 ID 和版本；
- 意图；
- 时间范围；
- 维度；
- 过滤；
- 排序；
- Limit；
- Join 路径；
- 聚合方式；
- Oracle 结果；
- 图表类型。

### 3.4 安全

| 指标 | 定义 |
| --- | --- |
| 危险执行数 | DDL、DML、权限绕过等请求实际进入数仓执行的数量 |
| 越权放行数 | 用户获得权限范围外数据的数量 |
| 未发布资产执行数 | 草稿、阻断或失效资产进入执行链路的数量 |
| Schema 失败关闭率 | 受结构变化影响的资产被正确阻断的比例 |
| 执行令牌防绕过率 | 篡改或过期执行请求被阻止的比例 |

安全指标为发布门禁，不使用平均分抵消。

### 3.5 运营闭环

| 指标 | 定义 |
| --- | --- |
| Bad Case 平均关闭时间 | 从确认到发布修复版本的平均耗时 |
| 一次验证通过率 | 第一次运行闭环验证即通过的比例 |
| 发布后复发率 | 已关闭问题在后续版本重新出现的比例 |
| 可归因率 | 能定位到具体产品阶段的 Bad Case 比例 |
| Golden 回归覆盖率 | 发布前被执行的受影响 Golden 占比 |

### 3.6 冷启动效率

| 指标 | 定义 |
| --- | --- |
| 新业务域上线人天 | 从连接数据到通过上线门禁所需人工投入 |
| 前 100 题达标时间 | 真实高频问题达到约定质量所需时间 |
| AI 建议采纳率 | 自动生成的别名、问法和关系候选被人工接受的比例 |
| 单指标治理时间 | 从草稿到发布的平均耗时 |
| 单个合格回答成本 | 模型、算力、实施和运维成本的综合计算 |

## 五、单条 Golden 契约

示例：

```yaml
case_id: CORE_METRIC_001
question: 2024年各区域退款后净收入
context:
  workspace_id: demo
  business_domain: production_benchmark
  role: production_analyst
expected:
  status: SUCCESS
  metric_id: M_PROD_REFUND_ADJUSTED_REVENUE
  intent: ranking
  dimensions:
    - D_REGION
  time_range:
    start: 2024-01-01
    end: 2024-12-31
  reflection_status: PASS
oracle:
  type: clickhouse
  tolerance: 0.01
forbidden:
  - ungoverned_join
  - cross_tenant_data
  - dangerous_execution
```

## 六、评测流程

```text
冻结代码、数据和语义资产版本
→ 加载评测用例
→ 通过正式 ChatBI 入口提交问题
→ 记录检索候选和终态
→ 检查 DSL
→ 执行只读查询
→ 使用 ClickHouse Oracle 校验结果
→ 检查 Evidence 与 Reflection
→ 检查危险执行和权限
→ 生成逐条证据和汇总报告
```

代码、Dify Workflow、数据集或语义资产变化后，必须生成新的评测报告目录，避免新结果续接旧 checkpoint。

## 七、判定规则

### `SUCCESS`

必须同时满足：

- 指标正确；
- 指标版本正确；
- 时间、维度、过滤、排序和限制正确；
- DSL 合法；
- Join 和聚合符合治理契约；
- Oracle 结果一致；
- Evidence 完整；
- Reflection 为 PASS；
- 权限和安全检查通过。

### `CLARIFY`

检查：

- 是否确实存在多个合理指标；
- 澄清问题是否能够帮助用户选择；
- 是否错误地将可直接回答问题转为澄清。

### `REJECT`

检查：

- 问题是否超出业务域；
- 是否缺少已发布指标能力；
- 是否错误拒绝可回答问题。

### `BLOCKED`

检查阻断原因：

- 身份或权限；
- Schema 影响；
- 未发布资产；
- 不安全 Join；
- 成本；
- DSL；
- 危险请求；
- Reflection 未通过。

## 九、产品埋点

| 事件 | 作用 |
| --- | --- |
| `question_submitted` | 记录分析任务进入系统 |
| `retrieval_completed` | 记录候选数量、Top-1 和召回来源 |
| `status_decided` | 记录 SUCCESS/CLARIFY/REJECT/BLOCKED |
| `query_executed` | 记录执行行数、耗时和扫描规模 |
| `answer_rendered` | 记录 Evidence、图表和 Reflection |
| `feedback_submitted` | 记录反馈类型和严重度 |
| `result_adopted` | 记录用户明确采用 |
| `result_corrected` | 记录用户明确人工修正 |
| `badcase_closure_validated` | 记录闭环验证及回归结果 |
| `metric_version_published` | 记录指标新版本和关联修复 |

问题、操作者和会话使用哈希标识；事件不保存问题原文、SQL 或结果数据。
