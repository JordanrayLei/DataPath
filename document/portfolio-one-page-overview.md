# AI 数据运营平台｜一页作品集总览

> 适用场景：AI 产品经理作品集首页、简历项目附件、面试开场介绍。  
> 当前定位：作品集 MVP，已完成本地可运行闭环；不宣称已达到企业生产上线标准。  
> 本地演示入口：`http://127.0.0.1:8010/`

## 1. 项目一句话

面向业务运营、增长、商品、投放等角色的 AI 数据运营平台。用户用自然语言提出取数和分析需求，系统通过指标中心、Query DSL、安全 SQL 编译、数仓执行、Evidence 和 Reflection 校验，输出可追溯的数据、图表和业务解读，避免直接 NL2SQL 带来的口径混乱和 AI 编造风险。

## 2. 我的角色

独立 AI 产品经理 / 独立开发者。

- 负责需求定义、产品架构、用户链路、指标体系、可信 AI 链路设计。
- 设计并落地产品前端、ChatBI BFF、指标中心、数仓模拟层、Dify 内部编排链路和自动测评闭环。
- 将用户反馈设计为 Badcase，并进一步沉淀为黄金问题和回归评测资产。
- 明确区分已跑通能力、作品集模拟能力和生产化后续规划，避免过度包装。

## 3. 目标用户与核心痛点

| 用户 | 典型场景 | 当前痛点 |
| --- | --- | --- |
| 业务运营 | 看 GMV、订单、转化、地区排行 | 不会 SQL，依赖数据分析师排期 |
| 增长 / 投放 | 看广告消耗、ROI、转化效果 | 指标分散，口径经常不一致 |
| 数据产品 / 分析团队 | 支撑大量临时取数需求 | 重复问数多，解释和校验成本高 |
| 管理者 | 快速理解经营异常 | 只看数字不够，需要可信解释和证据 |

核心问题不是“让 AI 写 SQL”，而是“让业务用户安全、可追溯地自助获得可信数据答案”。

## 4. 解决方案

产品采用“AI 理解 + 确定性执行 + 可信校验”的设计：

```text
自然语言问题
  → 指标中心检索
  → Query DSL 结构化表达
  → SQL 安全编译
  → 数仓执行
  → 结果画像
  → Evidence 证据绑定
  → Reflection 可信校验
  → 图表 / 表格 / 业务解读
```

Dify 在项目中作为内部 AI 编排方案之一，不直接作为用户入口。真正面向业务用户的是独立前端和 `/api/chatbi/ask` BFF，这样可以把权限、指标口径、SQL 安全、Evidence 和测评能力沉淀在服务端。

## 5. 核心功能

| 模块 | 已实现能力 | 产品价值 |
| --- | --- | --- |
| 自然语言取数 | 支持趋势查询、排行查询、歧义澄清、未知指标拒绝 | 业务用户无需 SQL 即可取数 |
| 指标口径中心 | 展示指标定义、别名、公式、维度、语义模型、血缘字段 | 避免 AI 自行发明指标口径 |
| Query DSL | 用强类型 DSL 表达查询意图、指标、维度、时间范围 | 将 LLM 输出约束为可校验结构 |
| SQL 安全编译 | 服务端根据 DSL 生成 SQL，不暴露任意 SQL 入口 | 降低注入、越权和幻觉风险 |
| Evidence | 将数值发现绑定指标版本、时间、维度、Query ID 和行引用 | 让业务解读可追溯 |
| Reflection | 检查 Evidence、单位、数字一致性、敏感信息和无依据因果 | 阻断不可信解释 |
| Badcase 看板 | 用户可提交反馈，并推进状态 | 把问题运营起来，而不是只做一次性回答 |
| 黄金问题集 | 已确认 Badcase 可沉淀为可复跑用例 | 支撑后续规则、Prompt、指标变更回归 |
| 测评看板 | 展示最新评测、可信门禁和历史趋势 | 证明产品质量可持续追踪 |

## 6. 已验证结果

截至 2026-07-10，本地演示环境已完成以下验证：

- 产品前端可通过 `http://127.0.0.1:8010/` 访问。
- `/api/chatbi/ask` 可跑通自然语言取数主链路。
- 指标中心已有 24 个首发指标，覆盖电商经营和广告投放场景。
- 本地数据底座包含 PostgreSQL、ClickHouse、Redis，以及可复现演示数据。
- 自动测评覆盖成功链路、排行链路、歧义澄清、未知指标拒绝、workspace 拦截、内部接口鉴权、指标口径、Badcase、黄金问题和测评看板。
- 最新本地 live 测评结果：10/10 通过。
- 测评趋势接口可展示历史快照、通过率、失败门禁和平均耗时。

## 7. 产品亮点

1. 不是简单聊天机器人，而是面向数据运营的可信 AI 工作台。
2. 不是直接 NL2SQL，而是指标中心 + DSL + SQL Compiler 的受控链路。
3. 不是只返回答案，而是同时返回 Evidence、图表、表格和 Reflection 校验。
4. 不是一次性 Demo，而是包含 Badcase、黄金问题、回归测评和趋势看板的持续运营闭环。
5. Dify 被定位为内部编排层，产品入口和可信后端能力可以独立运行。

## 8. 当前边界

这是作品集 MVP，不是企业生产上线版本。

- 用户权限当前按公开演示用户处理，尚未实现完整企业级 SSO / RBAC。
- 数据为可复现演示数据，不接入真实企业生产数据。
- 指标治理后台尚未完整实现审批流、Owner 工作台和变更影响分析。
- 高可用、限流、审计、监控告警仍属于生产化后续规划。
- 前端为轻量原生 SPA，尚未迁移到完整 React / Vue 工程。

## 9. 下一步优化方向

| 优先级 | 方向 | 原因 |
| --- | --- | --- |
| P0 | 指标变更影响分析 | 展示指标公式或口径变更会影响哪些黄金问题、历史查询和业务解释 |
| P1 | 更多黄金问题与质量指标 | 计算准确率、澄清率、拒绝率、平均耗时和回归通过率 |
| P1 | 评测报警与版本对比 | 标记某次规则、Prompt 或指标口径变更导致的质量波动 |
| P2 | 企业权限与审计 | 补齐 SSO、RBAC、操作日志和数据访问审计 |
| P2 | 前端工程化 | 迁移到 React / Vite，提升复杂工作台扩展能力 |

## 10. 面试开场话术

> 这个项目的目标不是做一个会聊天的 BI，而是做一个按生产化思路设计的 AI 数据运营平台。  
> 我把 AI 能力限制在语言理解和编排层，把指标口径、SQL 编译、数据执行和可信校验放在服务端。这样既能提升业务取数效率，又能避免直接 NL2SQL 带来的指标幻觉、SQL 风险和解释不可追溯问题。  
> 当前项目已经完成本地闭环，包括产品入口、指标中心、数仓执行、Evidence、Reflection、Badcase、黄金问题和自动测评趋势看板。
