# DataPath AI 工作流设计

DataPath 使用 Dify 编排 AI 问数流程，但不把业务口径、权限判断和数据执行交给工作流中的大模型节点。工作流的作用，是组织“语义理解—确定性校验—数据执行—结果解释”之间的协作，并保证每个风险分支都有明确出口。

![DataPath 受约束的可信 AI 问数工作流](assets/trusted-ai-query-workflow.svg)

## 1. 设计原则

这条工作流遵循三个原则：

1. **AI 处理语言的不确定性**：理解问题、在有限候选中判断指标、生成结构化查询意图和修订结果解读；
2. **确定性系统控制事实与执行**：候选范围、指标版本、权限、Query DSL、SQL 编译、只读执行和 Evidence 均由 DataPath 服务端校验；
3. **任何关键校验都不能被绕过**：不确定时进入澄清，超出范围时拒绝，权限、资产或执行异常时失败关闭。

Dify 因此是流程编排层，而不是数据决策层。大模型输出必须回到服务端门禁验证后，才能进入下一阶段。

## 2. 三类节点如何分工

| 节点类型 | 在工作流中的职责 | 不能做什么 |
| --- | --- | --- |
| AI 节点 | 预处理用户表达、有限候选裁决、生成 Query DSL 草稿、按校验意见修订解读 | 自行新增指标、直接生成并执行 SQL、绕过权限和门禁 |
| DataPath 服务节点 | 加载上下文、召回授权候选、验证裁决、校验 DSL、编译执行、生成 Evidence、验证解读 | 猜测用户真实意图 |
| 分支与结束节点 | 将结果收敛为继续、澄清、拒绝、阻断或成功 | 在校验失败后继续主链路 |

工作流中的每次服务调用都携带同一组 `workflow_run_id`、Request ID 和 Trace ID，使一轮问数可以从 Dify 节点追踪到后端调用、Query Run 和最终 Evidence。

## 3. 主链路

### 3.1 理解问题并收敛指标

| 阶段 | 输入 | 处理 | 输出 | 失败去向 |
| --- | --- | --- | --- | --- |
| 加载上下文 | 用户问题、身份、会话、业务域 | 服务端加载权限范围和上一轮查询条件 | 可用上下文 | 上下文异常 → `BLOCKED` |
| 问题预处理 | 用户问题、可用上下文 | AI 提取指标表达、时间、维度和筛选条件 | 结构化语义意图 | 结构不合法 → `REJECT` |
| 候选召回 | 语义意图、身份、业务域 | 仅召回已发布且有权访问的指标 | 候选集与签名令牌 | 无候选 → `REJECT` |
| 有限候选裁决 | 用户问题、上下文、候选集 | AI 只能在候选集内选择、澄清或拒绝 | 裁决草稿 | 低置信度 → `CLARIFY` |
| 裁决校验 | 裁决草稿、候选集、签名令牌 | 服务端验证指标 ID、版本和候选来源 | 已确认指标 | 篡改或越界 → `REJECT` |

候选集由服务端生成并签名。即使 AI 返回了一个看似合理的指标，只要它不在本轮候选集内，工作流也不会继续。

### 3.2 将语义意图变成可执行查询

| 阶段 | 输入 | 处理 | 输出 | 失败去向 |
| --- | --- | --- | --- | --- |
| Query DSL 草稿 | 已确认指标、时间、维度、筛选条件 | AI 将自然语言意图映射为受约束结构 | Query DSL 草稿 | 缺少必要条件 → `CLARIFY` |
| DSL 校验 | DSL 草稿、身份、语义资产版本 | 服务端校验指标、维度、Join、权限、粒度和资产状态 | 规范化 Query DSL | 任一门禁失败 → `BLOCKED` |
| 确定性编译 | 规范化 Query DSL | 服务端编译参数化 SQL，签发一次性执行令牌 | Query ID、执行令牌 | 编译失败 → `BLOCKED` |
| 只读执行 | Query ID、执行令牌 | 数仓只读执行，并限制超时和查询范围 | 查询结果 | 执行失败 → `BLOCKED` |

大模型看不到自由 SQL 执行入口。执行节点只接收服务端签发的执行令牌，不接受工作流直接传入任意 SQL。

### 3.3 从查询结果生成可信答案

| 阶段 | 输入 | 处理 | 输出 | 失败去向 |
| --- | --- | --- | --- | --- |
| 结果画像 | Query DSL、查询结果 | 服务端计算统计摘要、异常信息和 Evidence | 冻结的结果证据 | 证据不完整 → `BLOCKED` |
| 业务解读 | 结果画像 | 基于冻结证据生成结论、限制条件和下一步建议 | 解读草稿 | 进入 Reflection |
| Reflection | Query DSL、Evidence、解读草稿 | 服务端检查数值引用、口径、范围与证据一致性 | 通过或修订意见 | 不通过 → 修订一次 |
| 修订与二次校验 | 原解读、修订意见、Evidence | AI 仅按校验意见修订，再次执行 Reflection | 可信解读 | 仍不通过 → 仅返回数据与证据 |

二次 Reflection 仍未通过时，系统不会继续展示未经验证的业务结论，而是降级为数据与 Evidence。这使“查询成功”和“解读可信”成为两个独立门禁。

## 4. 工作流中的关键分支

| 分支 | 何时触发 | 用户看到什么 | 是否执行查询 |
| --- | --- | --- | --- |
| `CLARIFY` | 多个指标候选都合理，或缺少必要条件 | 有限选项和一个明确问题 | 否 |
| `REJECT` | 无治理候选、问题超出业务域，或 AI 选择越界 | 能力边界和改写建议 | 否 |
| `BLOCKED` | 权限、Join、资产状态、DSL、执行或 Evidence 校验失败 | 不泄露敏感信息的阻断说明 | 否或立即停止 |
| 数据降级 | 查询结果有效，但两次解读均未通过 Reflection | 数据、图表和 Evidence，不展示未经验证的结论 | 是 |
| `SUCCESS` | 指标、查询、执行、Evidence 和解读全部通过 | 答案、图表、口径和执行证据 | 是 |

这些分支不是异常补丁，而是工作流的一部分。DataPath 不以“尽量让每轮都成功”为目标，而是让每轮都进入一个可以解释、可以追踪的产品终态。

## 5. 为什么采用这种工作流

如果完全由大模型生成 SQL，链路短，但指标口径、权限和 Join 风险难以稳定控制；如果完全依赖规则，执行可控，却很难处理真实业务语言和多轮表达。

DataPath 将两者拆开：

- Dify 让语义节点、服务节点和分支门禁可以被直观看见和独立调试；
- DeepSeek 只参与需要语言判断的环节；
- DataPath 后端保留事实、权限、执行和验证权；
- 统一 Trace 将工作流运行与 Query Run、反馈和后续测评连接起来。

这种设计牺牲了一部分“自由回答率”，换取更清晰的责任边界、更稳定的失败行为，以及可以进入持续质量闭环的运行证据。
