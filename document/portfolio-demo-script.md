# AI 数据运营平台作品集演示脚本

> 适用场景：AI 产品经理作品集展示、项目答辩、面试项目讲解。  
> 当前验证入口：`http://127.0.0.1:8010/`  
> 核心原则：讲真实已跑通的能力，不把规划、模拟和未完成能力说成已上线生产。

## 1. 一句话介绍

这是一个面向业务运营的 AI 数据运营平台。用户用自然语言提出取数和分析需求，系统不会让 LLM 直接写 SQL，而是通过指标中心、Query DSL、确定性 SQL 编译、数仓执行、结果画像、Evidence 和 Reflection 校验，输出可追溯的数据、图表和业务解读。

## 2. 30 秒项目定位

可以这样开场：

> 这个项目的目标不是做一个聊天机器人，而是做一个生产化思路的 AI 数据提效工具。  
> Dify 在这里是内部编排链路之一，真正给业务用户使用的是独立前端入口。  
> 我重点解决三个问题：第一，业务人员不会 SQL 也能自助取数；第二，指标口径不清时不乱查；第三，所有数值解读都有 Evidence 和 Reflection 校验，避免 AI 编造。

## 4. 8 分钟现场演示路径

### 4.1 演示一：GMV 月趋势闭环

输入：

```text
最近一年每月 GMV 趋势如何？
```

预计结果：

- 状态：成功。
- 指标：`M_SALES_GMV`。
- DSL 意图：`trend_query`。
- 图表：折线图。
- 数据行数：12 行。
- Evidence：3 条。
- Reflection：PASS。

讲解口径：

> 这里不是直接 NL2SQL。前端把问题提交给 `/api/chatbi/ask`，服务端先加载上下文和权限，再做指标检索。  
> 命中 GMV 后，系统生成强类型 Query DSL，再由后端 Compiler 编译 SQL。SQL 不返回给浏览器。  
> 数仓执行后，Result Profiler 生成趋势摘要、异常点和 Evidence。最后业务解读会经过 Reflection 校验，通过后才展示给用户。

重点指给面试官看：

- 左侧执行链路：上下文加载、指标检索、DSL 校验、SQL 编译、数仓执行、结果画像、业务解读、Reflection。
- 右侧图表和数据表。
- Evidence ID 与业务解读中的引用关系。
- 技术追踪里的 Query ID、DSL、Reflection 状态。

### 4.2 演示二：地区 GMV 排行

点击示例或输入：

```text
各地区 GMV 排名
```

预计结果：

- 状态：成功。
- 指标：`M_SALES_GMV`。
- DSL 意图：`ranking_query`。
- 维度：`D_REGION`。
- 图表：柱状图。
- 数据行数：4 行。
- Evidence：5 条。
- Reflection：PASS。

讲解口径：

> 这一步说明平台不是只写死了一个 GMV 月趋势样例。  
> 同一个入口可以根据问题结构生成不同 DSL：上一条是趋势查询，这一条是排行查询。  
> 前端只是产品入口，真正的查询约束、指标权限、SQL 安全和 Evidence 生成都在服务端。

### 4.3 演示三：指标歧义澄清

点击示例或输入：

```text
看看毛利
```

预计结果：

- 状态：需澄清。
- 候选：毛利额、毛利率。
- 不生成 DSL。
- 不编译 SQL。
- 不执行数仓查询。

讲解口径：

> 这是我认为 AI 数据产品最关键的地方之一：不确定时不能假装确定。  
> “毛利”在业务里可能指毛利额，也可能指毛利率，所以系统进入 CLARIFY，而不是随便选一个指标去查。  
> 这体现了指标中心和置信度门控的价值。

### 4.4 演示四：未知指标拒绝

输入：

```text
最近一年每月火星销售指数
```

预计结果：

- 状态：拒绝或未命中。
- 不生成 DSL。
- 不编译 SQL。
- 不执行查询。

讲解口径：

> 这个例子展示 fail-closed 设计。  
> 如果指标中心没有授权、已发布、可执行的指标，系统不会让 LLM 自己发明一个“火星销售指数”。  
> 对数据产品来说，拒绝错误请求比返回一个看似合理但不可追溯的答案更重要。

### 4.6 演示五：提交 Badcase 反馈

在任意成功结果页底部填写：

```text
类型：解读不可信
严重程度：高
问题描述：解读没有解释异常月份的业务背景。
期望表现：希望提示需要补充活动日历。
```

预计结果：

- 页面提示：已进入候选。
- 后端返回 `feedback_id`。
- 反馈记录落到 `audit.user_feedback`。
- 若关联了 Query ID，则标记为 `regression_candidate=true`。
- Badcase 看板刷新后能看到该反馈。
- 可以将状态从 `OPEN` 推进到 `CONFIRMED` 或 `FIXED`。

讲解口径：

> AI 数据产品不能只做一次性回答，还要能把用户发现的问题沉淀成 Badcase。  
> 这条反馈会关联 Query ID、原始问题、反馈类型、严重程度、页面上下文和查询快照。  
> 后续可以把这些 Badcase 转成黄金问题或回归集，用来验证指标检索、DSL、Evidence 和解释是否被修好。

### 4.7 演示六：转为黄金问题并运行回归评测

在 Badcase 看板中，将一条已确认反馈推进到 `CONFIRMED` 后点击“加入黄金集”，再在“黄金问题集 / 回归评测”面板点击“运行回归评测”。

预计结果：
- 生成一条 `golden_id`。
- 黄金问题记录落到 `audit.golden_question`。
- 系统保存该问题当次成功链路的期望结构，包括状态、指标、DSL intent、维度、图表、行数和 Reflection 状态。
- 回归评测重新调用 `/api/chatbi/ask`，并与黄金问题期望结构比对。
- 评测通过时展示 `PASS`、通过数、总数和每条用例耗时。

讲解口径：
> 这一步展示的是 AI 数据产品的持续运营闭环。  
> 用户反馈不是只存一条工单，而是可以沉淀为黄金问题。后续每次改指标检索、DSL 生成、解释逻辑或 Dify 编排，都可以复跑这些黄金问题，避免修一个 Badcase 又引入新的回归问题。

### 4.8 演示七：指标口径中心

预计结果：

## 5. 架构讲解口径

推荐用这段解释整体设计：

> 我把系统分成四层：  
> 第一层是产品前端入口，负责提问、展示链路状态、图表、数据、Evidence 和调试追踪。  
> 第二层是 ChatBI BFF，也就是 `/api/chatbi/ask`，它保护内部 token，并把一次用户问题编排成完整链路。  
> 第三层是可信 ChatBI 服务，包括上下文、指标检索、DSL 校验、SQL 编译、数仓执行、结果画像、业务解读和 Reflection。  
> 第四层是基础设施，包括 PostgreSQL 指标中心、ClickHouse 数仓、可复现演示数据和 Dify workflow。  
> Dify 不是用户入口，而是内部 AI 编排方案之一；项目的产品入口和可信后端链路可以独立运行。

## 6. 可以主动强调的产品设计点

### 6.1 为什么不直接 NL2SQL

> 直接 NL2SQL 的问题是口径、权限和安全都不可控。  
> 所以我让 LLM 只做语言理解，核心口径来自指标中心，查询表达用强类型 DSL，SQL 只能由服务端 Compiler 生成。

### 6.2 为什么需要 Evidence

> AI 解读看起来很顺，但如果没有证据绑定，很难判断它是不是编的。  
> 所以每条数值发现都必须引用 Evidence ID，Evidence 记录指标版本、值、单位、时间范围、维度、Query ID 和行引用。

### 6.3 为什么需要 Reflection

> Reflection 是最后一道可信输出门。  
> 它会检查未知 Evidence、数字不匹配、单位不匹配、时间范围不匹配、敏感信息和无依据因果表达。  
> 通过才展示完整解读，否则要求修订或降级为仅数据输出。

### 6.4 为什么前端不直接调用 Dify

> Dify 适合内部编排，但不适合作为这个项目唯一的产品入口。  
> 业务用户需要的是一个能看链路状态、图表、Evidence、结果表和测评追踪的产品工作台。  
> 所以前端调用 BFF，BFF 再保护性地串联内部链路。

## 7. 面试常见追问与回答边界

### Q1：这个项目是不是已经生产可用？

建议回答：

> 它是作品集 MVP，按生产化思路设计并完成本地闭环，但我不会说它已经达到企业生产上线标准。  
> 目前已验证的是本地演示环境、指标中心、数仓执行、前端入口和自动测评。  
> 真正生产上线还需要企业 SSO、完整 RBAC、审计、限流、高可用、更多数仓适配和持续 Badcase 运营。

### Q2：Dify 在这里到底承担什么角色？

建议回答：

> Dify 是 AI 编排层，用来表达复杂工作流和 LLM 节点。  
> 但项目的核心可信能力不依赖 Dify 单点：指标检索、DSL 校验、SQL 编译、数仓执行、Evidence 和 Reflection 都是后端服务。  
> 这样做的好处是 Dify 插件或模型流式响应不稳定时，产品仍然有可运行的后端 fallback。

### Q3：你的指标平台做到了什么程度？

建议回答：

> MVP 阶段实现了指标元数据、版本、别名、业务域、语义模型、维度支持关系和指标检索。  
> 首批有 24 个指标，覆盖电商经营和广告投放。  
> 还没有做完整的指标治理后台，比如审批流、血缘可视化、Owner 工作台和变更影响分析，这些是后续规划。

### Q4：权限为什么现在看起来比较简单？

建议回答：

> 这是根据作品集阶段做的取舍。用户之前定义过可以先不做复杂用户权限，所以当前使用公开演示用户 `public_demo_user`，默认能查看两个业务域的非敏感聚合数据。  
> 但系统保留了 workspace、operator、row_policy_token 和内部 service token 机制，并且测评里验证了内部接口不会被浏览器无 token 调用。

### Q5：怎么证明不是写死 demo？

建议回答：

> 我准备了不同类型用例：月趋势、地区排行、歧义澄清、未知指标拒绝、workspace 拦截和内部接口鉴权。  
> 月趋势和地区排行走的是不同 DSL intent、不同维度和不同图表。  
> 同时保留了 Query ID、Evidence、DSL 和测评报告，可以复现验证。

- 前端是轻量原生 SPA，不是完整 React/Vue 工程。

1. 引入更多黄金问题，计算准确率、澄清率、拒绝率和平均耗时。

3. 增加黄金问题版本管理，记录每次规则或 Prompt 调整前后的通过率变化。
4. 增加指标变更影响分析，展示某个指标公式变化会影响哪些黄金问题和历史查询。
5. 增加评测报警和版本对比，标记某次规则、Prompt 或指标口径变更导致的质量波动。

## 9. 演示失败时的兜底说明

如果前端页面打不开：

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8010
```

如果 8010 端口被旧进程占用：

```powershell
netstat -ano | findstr ":8010"
Stop-Process -Id <PID> -Force
```

如果 Dify 插件或 DeepSeek 流式响应不稳定：

> 这正是项目里增加后端 Evidence fallback 的原因。  
> 业务解读可以由服务端确定性生成，再交给 Reflection 校验，保证演示主链路稳定闭环。

如果测评需要重新生成：

```powershell
.\.venv\Scripts\python.exe scripts\evaluate_chatbi_entrypoint.py --base-url http://127.0.0.1:8010 --report-name chatbi-entrypoint-evaluation-live-8010
```
