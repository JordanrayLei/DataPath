# AI 数据运营平台｜产品决策说明文档

> 适用场景：AI 产品经理面试追问、作品集深度说明、项目答辩。  
> 核心目的：解释这个项目为什么不是简单 NL2SQL Demo，而是一个按生产化思路设计的可信 AI 数据产品。

## 1. 决策摘要

| 决策 | 选择 | 不选择 | 核心原因 |
| --- | --- | --- | --- |
| 用户入口 | 独立前端 + ChatBI BFF | 直接让用户进入 Dify | 业务用户需要稳定产品入口、链路状态、图表、Evidence 和反馈闭环 |
| AI 取数方式 | 指标中心 + Query DSL + SQL Compiler | 让 LLM 直接写 SQL | 控制指标口径、权限、安全和可解释性 |
| 指标来源 | 指标中心作为唯一可信事实源 | 让模型自由理解指标 | 避免指标幻觉和同名口径误用 |
| 查询表达 | 强类型 Query DSL | 自由文本 SQL 或半结构化 Prompt | 便于校验、编译、回归和审计 |
| 可信输出 | Evidence + Reflection | 只返回自然语言结论 | 让数字、图表和解释可追溯、可阻断 |
| 质量运营 | Badcase → 黄金问题 → 回归测评 → 趋势看板 | 只做一次性 Demo | 让 AI 数据产品具备持续迭代闭环 |
| 权限策略 | MVP 阶段公开演示用户 + 服务端保护机制 | 一开始做完整企业 RBAC | 作品集阶段优先证明核心链路，保留生产化扩展口 |

## 2. 决策一：为什么不直接做 NL2SQL？

### 背景

自然语言转 SQL 是最直观的 ChatBI 路径，但在真实业务里存在三个高风险问题：

1. 指标口径不稳定：同一个词可能对应多个指标，例如“毛利”可能是毛利额，也可能是毛利率。
2. SQL 安全不可控：如果让模型直接生成 SQL，容易出现越权查询、错误 JOIN、字段误用或注入风险。
3. 解释不可追溯：即使 SQL 能跑通，业务用户也难以判断数字和解释是否可靠。

### 产品选择

本项目不让 LLM 直接写 SQL，而是采用：

```text
自然语言理解 → 指标检索 → Query DSL → 服务端 SQL Compiler → 数仓执行
```

LLM 只负责语言理解和结构化意图生成；指标口径、SQL 生成和执行由服务端确定性模块控制。

### 产品收益

- 可控：指标只能来自已发布、授权、可执行的指标中心。
- 可校验：DSL 可以被 JSON Schema 和业务规则校验。
- 可审计：每次查询都有 Query ID、指标 ID、维度、时间范围和 Evidence。
- 可回归：黄金问题可以复跑并比对 DSL intent、指标、图表、行数和 Reflection 状态。

### 取舍

这种方案比直接 NL2SQL 复杂，前期需要建设指标中心、DSL 和 Compiler。但它更贴近真实公司的数据产品，因为企业更在意稳定口径、安全边界和长期治理，而不是一次性生成一条看似可用的 SQL。

## 3. 决策二：为什么 Dify 不是用户入口？

### 背景

Dify 很适合快速搭建 AI workflow，也适合承载 LLM 节点、工具调用和编排逻辑。但它天然更偏“内部编排平台”，不一定适合作为最终业务用户工作台。

业务用户真正需要的是：

- 可以提问的产品入口。
- 可视化链路状态。
- 图表、表格和业务解读。
- Evidence 和调试信息。
- Badcase 反馈入口。
- 测评和质量趋势。

### 产品选择

本项目将 Dify 定位为内部编排链路之一，而不是唯一用户入口。

最终用户访问独立前端，前端调用 `/api/chatbi/ask` BFF。BFF 再负责串联后端可信链路，必要时可与 Dify workflow 对接。

### 产品收益

- 用户体验更稳定：前端可以按业务场景设计工作台，而不是暴露 workflow 页面。
- 安全边界更清晰：内部 service token、权限、SQL 编译和数据访问都在服务端控制。
- 可替换性更强：如果 Dify 插件、模型或流式响应不稳定，后端 Evidence fallback 仍能保障主链路演示。
- 作品集表达更产品化：Dify 是实现方式之一，不是产品本身。

### 面试表达

> 我没有把 Dify 当成产品入口，而是把它当成内部 AI 编排能力。业务用户看到的是一个数据运营工作台；Dify 负责 workflow，后端负责可信能力，前端负责产品体验。

## 4. 决策三：为什么必须有指标中心？

### 背景

AI 数据产品最容易出问题的地方不是“不会回答”，而是“回答了一个看似合理但口径错误的答案”。

例如：

- GMV 是支付金额还是下单金额？
- ROI 是广告 ROI 还是整体营销 ROI？
- 毛利是毛利额还是毛利率？
- 同一个指标能否按地区、渠道、月份拆分？

如果没有指标中心，LLM 会根据语义猜测指标，结果很难稳定。

### 产品选择

指标中心作为唯一可信事实源，沉淀：

- 指标 ID、名称、别名。
- 业务域、指标类型、单位。
- 口径说明和公式。
- 可用维度。
- 语义模型。
- 数仓血缘表和字段。
- 版本和 Owner 信息。

### 产品收益

- 降低指标误用率。
- 支持歧义澄清，而不是强行查询。
- 支持未知指标拒绝，而不是模型发明指标。
- 支持后续指标治理、审批、变更影响分析。

### 已验证场景

- 用户问“最近一年每月 GMV 趋势如何？”时，系统选择 `M_SALES_GMV` 并生成趋势查询。
- 用户问“看看毛利”时，系统进入澄清状态，而不是随便选择一个指标。
- 用户问“火星销售指数”时，系统拒绝执行，避免生成虚假口径。

## 5. 决策四：为什么设计 Query DSL？

### 背景

如果前端直接把自然语言交给模型，后端拿到的只是不可控文本。要把 AI 取数做成产品，就需要一种中间表达，把用户意图变成可验证、可编译、可回归的结构。

### 产品选择

设计 Query DSL 作为自然语言和 SQL 之间的契约层。

DSL 负责表达：

- 查询意图：趋势、排行、聚合等。
- 指标 ID。
- 维度。
- 时间范围。
- 筛选条件。
- 排序和限制。
- 图表建议。

### 产品收益

- 对产品：DSL 是稳定接口，前端、后端、Dify 和测评可以围绕它协作。
- 对安全：SQL 只能由服务端 Compiler 根据 DSL 生成。
- 对质量：测评可以比对 DSL intent、维度、图表和行数。
- 对扩展：后续可以支持更多数仓引擎，只需扩展 Compiler。

### 取舍

DSL 会增加抽象层成本，但它让系统从“模型输出 SQL”升级为“AI 辅助生成可治理查询意图”。这更符合企业级数据产品的长期演进。

## 6. 决策五：为什么需要 Evidence 和 Reflection？

### 背景

AI 数据解读的风险不只在 SQL，还在最后的自然语言解释。

常见问题包括：

- 数字引用错。
- 单位错。
- 把相关性说成因果。
- 引用了结果中不存在的数据。
- 对敏感数据做了不合规解释。

### 产品选择

本项目把可信输出拆成两层：

1. Evidence：为每个数值发现绑定指标版本、值、单位、时间范围、维度、Query ID 和行引用。
2. Reflection：在输出前检查 Evidence、数字一致性、单位、时间范围、敏感信息和无依据因果表达。

### 产品收益

- 业务用户可以追溯“这个结论来自哪里”。
- 系统可以在不可信时降级、修订或阻断输出。
- 面试展示时可以解释：AI 不是只负责说得像，而是要说得有证据。

### 面试表达

> 我把 Evidence 当成 AI 数据产品的“引用系统”，把 Reflection 当成最后一道可信输出门禁。没有 Evidence 的解释不能直接展示给业务用户。

## 7. 决策六：为什么要做 Badcase、黄金问题和回归测评？

### 背景

AI 产品上线后一定会遇到误召回、误拒绝、口径不清、解释不准等问题。如果没有持续运营机制，产品只能靠手工修 Prompt，质量会越来越不可控。

### 产品选择

本项目设计了一个质量运营闭环：

```text
用户反馈 Badcase
  → 看板筛选与状态推进
  → 已确认 Badcase 转为黄金问题
  → 回归评测复跑
  → 测评看板展示最新结果
  → 趋势视图观察质量变化
```

### 产品收益

- 用户反馈不只是工单，而是可沉淀为测试资产。
- 每次改指标检索、DSL 规则、Prompt 或 Dify workflow 后，都可以复跑黄金问题。
- 趋势看板可以观察通过率、失败门禁和平均耗时变化。
- 产品经理可以用数据判断迭代是否真的提升质量。

### 已验证能力

- 成功查询后可提交 Badcase 反馈。
- Badcase 可进入看板并推进到 `CONFIRMED`。
- 已确认 Badcase 可生成黄金问题。
- 黄金问题可触发回归测评。
- 产品入口评测和 live 评测均已跑通 10/10。

## 8. 决策七：为什么当前权限先做简化？

### 背景

完整企业权限包含 SSO、RBAC、行列级权限、审计、数据脱敏和审批流。它们非常重要，但不是这个作品集 MVP 的第一优先级。

当前项目的核心验证目标是：

- AI 取数链路是否可信。
- 指标口径是否可控。
- SQL 是否由服务端安全生成。
- 结果是否可追溯。
- 质量是否可持续测评。

### 产品选择

MVP 阶段采用公开演示用户 `public_demo_user`，默认开放 demo 工作空间内的非敏感聚合数据。同时保留：

- workspace 参数。
- operator。
- row policy token 设计。
- 内部 service token。
- 非 demo workspace 拦截测评。
- 内部接口无 token 拒绝测评。

### 产品收益

- 优先展示核心产品价值，不被权限工程拖慢。
- 面试时能清楚解释作品集边界。
- 后续可以自然扩展到企业权限体系。

### 面试表达

> 权限我没有假装做完整企业级 RBAC。当前是作品集 MVP，所以用公开演示用户验证主链路；但我保留了 workspace、operator、row policy token 和 service token，并用测评证明内部接口不会被浏览器无 token 调用。

## 9. 决策八：为什么要做测评看板和趋势？

### 背景

AI 产品的质量不是一次演示成功就够了。模型、Prompt、指标口径、Dify workflow 或后端规则变化，都可能引发回归。

### 产品选择

项目内置产品入口测评脚本，并在前端展示：

- 最新测评状态。
- 产品用例结果。
- 安全 / 可信门禁。
- 历史快照。
- 通过率趋势。
- 平均耗时。
- 失败门禁数。

### 产品收益

- 面试官能看到产品不是“截图式 Demo”，而是有质量门禁。
- 质量从“主观感觉”变成“可观察指标”。
- 后续可以扩展为版本对比、报警和影响分析。

## 10. 当前边界与生产化规划

### 已完成

- 独立产品前端。
- `/api/chatbi/ask` BFF。
- 指标中心 MVP。
- Query DSL。
- SQL 安全编译和数仓执行。
- Result Profiler、Evidence、Reflection。
- Dify 本地 workflow 导入与联调。
- Badcase 反馈与看板。
- 黄金问题和回归评测。
- 测评看板和趋势视图。

### 未宣称完成

- 企业级 SSO / RBAC。
- 完整审计和操作留痕。
- 高可用部署。
- 真实生产数据接入。
- 指标审批流和 Owner 工作台。
- 完整数据血缘可视化。
- 多租户隔离。

### 下一步优先级

1. 指标变更影响分析：展示某个指标口径变化会影响哪些黄金问题、历史查询和业务解释。
2. 质量指标体系：准确率、澄清率、拒绝率、平均耗时、回归通过率。
3. 版本对比：标记规则、Prompt、指标口径变更前后的质量波动。
4. 企业权限：SSO、RBAC、审计、限流和数据访问策略。
5. 前端工程化：迁移到 React / Vite，支持更复杂的产品工作台。

## 11. 可以在面试中主动强调的能力

### AI 产品能力

- 能区分“AI 能做什么”和“产品应该让 AI 做什么”。
- 能设计 fail-closed 链路，不让模型在不确定时强行输出。
- 能把 Badcase 转成黄金问题和回归资产。

### 数据产品能力

- 理解指标口径、维度、血缘和数仓执行的关系。
- 不把 ChatBI 简化为 NL2SQL，而是围绕指标治理设计。
- 能解释为什么企业数据产品需要审计、权限和质量门禁。

### 产品落地能力

- 有可运行 Demo，而不是只停留在 PRD。
- 有产品验收和自动测评，而不是只看手工演示。
- 能诚实说明 MVP 边界和生产化差距。

## 12. 一句话总结

这个项目的核心产品判断是：AI 数据产品的关键不是让模型更自由地生成答案，而是让模型在指标、权限、SQL、安全和证据约束下生成可信答案，并通过 Badcase、黄金问题和测评趋势形成可持续运营闭环。
